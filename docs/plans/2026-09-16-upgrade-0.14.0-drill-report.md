### B2. 大檔分段傳輸

### B4. Production apply method 對齊 mini-drill

A–C 原演練的 staging managedFields 是 `manager: helm`、`operation: Apply`，即 Helm v4.3.0 auto mode 的 server-side apply。production release 則由 Helm 3 建立，revision 11 的 [operator 唯讀證據](https://github.com/WOOWTECH/Woow_k3s_omnigent_package/issues/3#issuecomment-5701639123)是 `manager: helm`、`operation: Update`；兩者 apply method 不同，不能把 A–C 結果稱為 client-side three-way merge 證據。

依驗收要求追加同版本、同 chart／override 的 mini-drill：先把 rev 7 server scale 0，再由 `scripts/apply.sh upgrade ... --server-side=false` 升同一 v0.14.0。`apply.sh` 以 `${@:2}` 把 flag 透傳給 `helm upgrade`。

```text

release revision=8 deployed
apply_end_utc=2026-09-16T17:24:03Z
helm get metadata --revision 8 APPLY_METHOD=client-side apply
schema migration keywords=absent（同版本，未跑 migration）
spec.replicas=1
readyReplicas=1
latest helm managedFields operation=Update
DB head=gg1b2c3d4e5f
Helm test=Succeeded
```

舊 `Apply` managedFields entry 仍保留；revision 8 新增的最新 Helm entry 是 `Update`（2026-09-16T17:23:30Z）。mini-drill **PASS**。WP-7 因此固定明帶 `--server-side=false`，並在步驟 11 後以唯讀 gate 要求 `spec.replicas=1`；不是 1 就 STOP，禁止手動 scale 1。

## FAIL／STOP 紀錄與 runbook 修正

| 事件 | 處置 | 結果 |

| go/no-go 觸發時 `apply.sh --wait` 尚未返回 | **WP-6 未演練**；不得宣稱已驗證 replicas=0 的 in-flight 行為 | runbook 預設等 apply 最長 30 分鐘自行返回後才進 B1 |
| pod 遺留未 scrub `pre-drill.dump` 與 18 個 parts | 依 live review 立即清除，並修正 drill log 不實記載 | 2026-09-16T17:20:12Z `find` 驗證殘留 0 |

## Go／no-go 建議

- Migration 絕對門檻：從 `Running database migrations...` 起算 **`max(migration ×3, 5 分鐘)`＝5 分鐘**，且不得晚於 T+45 分鐘。5 秒實測的 ×3 會退化成過短的 15.030 秒；production `DROP INDEX CONCURRENTLY` 可能被 anti-wraparound autovacuum 的 `ShareUpdateExclusiveLock` 阻擋。5 分鐘仍小於 setup-admin `activeDeadlineSeconds: 600` 與 startupProbe 900 秒。
- Rollback A Pod 等待上限：**11 分鐘**（204 ×3＝612 秒，向上取整）。
- startupProbe：維持 `periodSeconds: 10`、`failureThreshold: 90`。
- 任一大檔進出 pod 都用 32 MiB 分段，禁止退回單次大檔 `kubectl cp`。
