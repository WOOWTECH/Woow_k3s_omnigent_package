- pre-upgrade sessions：`blocking=[]`、`has_more=false`。
- pre-upgrade hosts：空陣列；runner 全部 parked。
- server scale 0 後 pod 已刪除，DB clients 為 0。
- staging pre-upgrade dump：71 秒、579,252,675 bytes、sha256 `1b0561f5caf149bc05da3ee9af335edfa49fcbf50a2d635dab86a27fdfa7c50f`；pod 內 catalog 與 full-read 均 PASS。

### B2. 大檔分段傳輸

單次 552 MiB `kubectl cp` 約 5.5 分鐘後被 API server 斷線；`--retries` 不會續傳。實測可用方式：

```bash
split -b 32m -a 3 /tmp/pre-0140.dump /tmp/pre-0140.part-
```

postgres `16-alpine` 使用 BusyBox，不能加 GNU `-d`。本次產生 18 段，以 alphabetic suffix lexical order 逐段 copy／`cat`：

```text

copy-out≈12s
remote/local bytes=579252675
remote/local sha256=1b0561f5caf149bc05da3ee9af335edfa49fcbf50a2d635dab86a27fdfa7c50f
result=PASS
```

pod 內 full-read 已在 dump 步驟完成；elmo 主機沒有 `pg_restore`，runbook 不依賴本機 full-read。

### B3. Migration 與正常路徑驗證

## FAIL／STOP 紀錄與 runbook 修正

| 事件 | 處置 | 結果 |
| --- | --- | --- |
| 單次大檔 `kubectl cp` 中斷 | 改為 32 MiB 分段；每次重組後比 bytes＋sha256 | 已回填步驟 8與 B1 |
| BusyBox `split` 不支援 `-d` | 依 STOP 規則請裁決；改用 `split -b 32m -a 3` | copy-out／copy-in 均 PASS |
| elmo 主機沒有 `pg_restore` | pod 內先 full-read，本機只做 bytes＋sha256；本機 full-read不是 runbook 條件 | 已在 runbook 說明 |
| `CHART` env 不被 `apply.sh` 使用 | staging 從 PR #16 worktree 執行；production 必須從 merge 後 main 執行 | 已在步驟 11說明 |

## Go／no-go 建議

- Migration 絕對門檻：從 `Running database migrations...` 起算 **1 分鐘**（5.010 ×3＝15.030 秒，向上取整為整數分鐘），且不得晚於 T+45 分鐘。
- Rollback A Pod 等待上限：**11 分鐘**（204 ×3＝612 秒，向上取整）。
- startupProbe：維持 `periodSeconds: 10`、`failureThreshold: 90`。
- 任一大檔進出 pod 都用 32 MiB 分段，禁止退回單次大檔 `kubectl cp`。
