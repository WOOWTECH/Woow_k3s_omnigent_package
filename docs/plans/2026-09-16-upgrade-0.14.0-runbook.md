# Omnigent v0.14.0 production 升級／rollback runbook

> 適用環境：`woow-k3s`／namespace `omnigent`／Helm release `omnigent`
>
> 升級路徑：v0.12.0（Alembic `ga1b2c3d4e5f`）→ v0.14.0（Alembic `gg1b2c3d4e5f`）
>
> 追蹤與證據：[pkg #3](https://github.com/WOOWTECH/Woow_k3s_omnigent_package/issues/3)

這是 production 維護窗口的逐行操作手冊。只有**叢集運維**能執行；其他人只可覆核文件與證據。所有命令都必須明帶 `--context woow-k3s`（Helm 用 `--kube-context woow-k3s`）且只作用於 namespace `omnigent`。唯一的 namespace 例外是步驟 9：只允許在 `longhorn-system` 建立／查詢本窗口命名的 Longhorn `Snapshot` CR；不得擴張成其他 Longhorn 寫入。

## 絕對禁止

- ⛔ 不得執行 `helm rollback`：migration 後把 image 退回 v0.12.0、但 DB 仍停在 `gg…`，server 會 crash-loop。
- ⛔ 不得使用 `--atomic`：逾時時自動回退 image，具有相同風險。
- ⛔ 不得執行 `kubectl set image`：會繞過 repo values 與 `scripts/apply.sh` 的 retain preflight。
- ⛔ 不得執行 `helm get values omnigent`：既有 revision 的 values 含明文帳密。
- ⛔ rollback 前 `OMNIGENT_FEATURES` 不可含 `canvas`；v0.12.0 不認得此 key。

每一步的完整 stdout／stderr、UTC 時間、執行指令與 exit code 都貼到 pkg #3；不得只貼摘要。

## 已量測 production 基線

初始基線來源：pkg #3 的 [唯讀量測 raw](https://github.com/WOOWTECH/Woow_k3s_omnigent_package/issues/3#issuecomment-5694462446) 與[備份定案](https://github.com/WOOWTECH/Woow_k3s_omnigent_package/issues/3#issuecomment-5694472346)。DB／dump 數字已依 [WP-7 實績](https://github.com/WOOWTECH/Woow_k3s_omnigent_package/issues/3#issuecomment-5707504039) 更新；規畫下一次窗口時不得沿用較小的 WP-6 staging 數字。

| --- | --- |
| Alembic | 升級前 `ga1b2c3d4e5f`；升級後 `gg1b2c3d4e5f` |
| DB | **3145 MB**（WP-7；初始量測為 2339 MB） |

| idle in transaction | 0 |

## 維護窗口實測與中斷預估

2026-09-16 revision 11 的 Recreate 實測與 2026-09-17 WP-7 production 實績提供下列窗口觀測基線：

- rev 11 Recreate 期間，cloudflared 約 28 秒回 HTTP 502、另有約 11 秒請求逾時，整段觀測到的服務中斷約 53 秒；**不是 404**。
- 舊 server pod 會等滿 30 秒 `terminationGracePeriodSeconds` 才結束。
- rev 11 的既有 hosts 6/6 在 server 回來後自動重連。
- `/health` 可用性一律用 GET（`curl -fsS https://omnigent.woowtech.io/health`）判斷；服務正常時 HEAD／`curl -sI` 仍會回 404，不能拿來判定 outage。
- WP-7 最終成功起跑由 scale 0 到 `/health` ok 約 **3 分 53 秒**，後續公告以「單次正常路徑約 4 分鐘」為實測基線，不再以 20–30 分鐘當成正常單次中斷。
- WP-7 因不明外部自動化把 server 拉起而兩度中止重跑，三段中斷累計約 **34 分鐘**。公告必須同時說明：單次約 4 分鐘不包含中止重跑；每次重跑都會把中斷時間累加，不得只報最後一次。

## WP-6 演練與 WP-7 production 實績

下表是後續 production go/no-go 的輸入；任何欄位在新一輪升級前失效或缺值都不得開窗。

| 項目 | 值 |
| --- | --- |
| dump 耗時 | **132 秒**（WP-7 production dump＋full-read，764015760 bytes；WP-6 為 112 秒／552 MiB） |
| migration 耗時 | WP-7 ≤5.52 秒（含 startup）；WP-6 最大 5.010 秒（三次為 4.997／4.774／5.010 秒） |
| Rollback A 耗時 | 204 秒（Alembic downgrade Pod，含 GIN 重建）；連續主動操作估算 249 秒 |
| Rollback B 耗時 | 343 秒（scale 0 到 v0.12.0 Helm test）；其中 restore 254 秒 |
| startupProbe `failureThreshold` | 90（維持；`periodSeconds: 10`，900 秒涵蓋 5 分鐘 go/no-go floor） |
| go/no-go 絕對門檻（`max(migration ×3, 5 分鐘)`，且不得晚於 T+45） | 從 `Running database migrations...` 起 5 分鐘，且不得晚於 T+45 分鐘 |
| A2 等待上限（Rollback A 實測 ×3 換算分鐘） | 11 分鐘（204 ×3＝612 秒，向上取整） |

來源：[WP-6 staging migration／rollback 演練報告](2026-09-16-upgrade-0.14.0-drill-report.md)與 [WP-7 production 驗收](https://github.com/WOOWTECH/Woow_k3s_omnigent_package/issues/3#issuecomment-5707504039)。WP-6 估算正常完整操作約 27 分 45 秒，WP-7 實際單次服務中斷約 4 分鐘；這兩個數字用途不同。最壞 rollback 路徑仍保留對外 90 分鐘窗口。migration ×3 對短秒數實測會退化成過度激進的門檻；production 的 `DROP INDEX CONCURRENTLY` 可能被 anti-wraparound autovacuum 的 `ShareUpdateExclusiveLock` 擋住，因此維持 5 分鐘 floor。

### WP-6 staging 銷毀補記（非 production 窗口步驟）

`longhorn` StorageClass 的 `reclaimPolicy` 是 `Retain`。刪除 staging PVC／namespace 只會讓對應 PV 進入 `Released`，**不會刪除 PV 或 Longhorn backend volume**。因此 staging 銷毀完成後，必須轉交叢集運維：

1. 列出 `Released` PV，逐顆確認 `spec.claimRef.namespace` **完全等於** `dev-sandbox-omnigent-stg`；不得只靠名稱猜測。
2. 記錄 5 顆 staging PV 與 Longhorn volume 的對應；其中 postgres volume 含 scrub 前 production dump restore 出來的資料，視為敏感 production 副本。
3. 僅由叢集運維刪除上述 Released PV 與對應 Longhorn volume，再確認兩者都不存在；stdout 貼 pkg #3。

staging agent 不得自行操作 cluster-scoped PV 或 `longhorn-system`。這段只記錄 WP-6 收尾教訓，不改變下方 WP-7 production 操作邊界。

**長等待回報規則：**不得把長等待轉到背景後無人監看。優先以前景輪詢；若必須使用背景任務，執行者要持續監看，完成或 STOP 時立即通知，且至少每 5 分鐘向 planner 回報 heartbeat。planner 超過 10 分鐘沒有收到回報要主動查詢，不得把沉默視為仍正常執行。

PR #4 的 startupProbe 必須存在，且 `failureThreshold × periodSeconds` 必須涵蓋 WP-6 表中的 5 分鐘 go/no-go floor。原因是 upstream `deploy/docker/entrypoint.py:536` 先執行 `run_migrations()`，`:545` 才啟動 uvicorn；migration 期間 `/health` 不回應。沒有 startupProbe 時，liveness 約四分鐘就會 SIGKILL 正在執行 `DROP INDEX CONCURRENTLY` 的 server pod。PR #4 硬編 `periodSeconds: 10` × `failureThreshold: 90`＝900 秒＝15 分鐘，涵蓋 5 分鐘 floor。不得把 failureThreshold 字面縮成 migration ×3 所需的 2；那會讓短期 production lock contention 重新暴露於 liveness kill。

```bash
STARTUP_FAILURE_THRESHOLD="$(kubectl --context woow-k3s -n omnigent get deployment \
  omnigent-server \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="server")].startupProbe.failureThreshold}')"
STARTUP_PERIOD_SECONDS="$(kubectl --context woow-k3s -n omnigent get deployment \
  omnigent-server \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="server")].startupProbe.periodSeconds}')"
printf 'startupProbe.failureThreshold=%s\nstartupProbe.periodSeconds=%s\n' \
  "$STARTUP_FAILURE_THRESHOLD" "$STARTUP_PERIOD_SECONDS"
test -n "$STARTUP_FAILURE_THRESHOLD" && test -n "$STARTUP_PERIOD_SECONDS" || {
  echo 'STOP: startupProbe failureThreshold／periodSeconds 不存在；PR #4 尚未落地，停止並查明' >&2
  false
}
```

### 步驟 1：建立證據與備份目錄

**執行者＝叢集運維｜證據＝貼 pkg #3**

在 operator 主機的 pkg 本機 clone 根目錄執行；備份目錄不得放在 repo、`/tmp` 或任何共享路徑。互動 shell 只開 `pipefail`，**不要開 `set -e`／`set -u`**，避免預期中的非零檢查直接關閉整個 shell 並丟失窗口變數。operator 主機必須提供 **bash 4+**（使用 `mapfile`）與 PATH 上的 **GNU coreutils** `stat`／`split`／`sha256sum`；macOS 預設 BSD 指令不符合。

```bash
set -o pipefail
export PATH="$HOME/.local/bin/helm4:$PATH"
STAT_VERSION="$(stat --version 2>/dev/null | head -1)"
SPLIT_VERSION="$(split --version 2>/dev/null | head -1)"
SHA_VERSION="$(sha256sum --version 2>/dev/null | head -1)"
if [ "${BASH_VERSINFO[0]}" -ge 4 ] \
  && [[ "$STAT_VERSION" = *'GNU coreutils'* ]] \
  && [[ "$SPLIT_VERSION" = *'GNU coreutils'* ]] \
  && [[ "$SHA_VERSION" = *'GNU coreutils'* ]]; then
  printf 'bash=%s\nstat=%s\nsplit=%s\nsha256sum=%s\n' \
    "$BASH_VERSION" "$STAT_VERSION" "$SPLIT_VERSION" "$SHA_VERSION"
  export PKG_REPO="$(pwd -P)"
  if [ ! -f "$PKG_REPO/charts/omnigent/Chart.yaml" ]; then
    echo 'STOP: 目前不在 pkg clone 根目錄，停止並查明' >&2
    false
  else
    export KUBECONTEXT=woow-k3s
    export NAMESPACE=omnigent
    export RELEASE=omnigent
    export STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
    export BACKUP_DIR="$HOME/secure/omnigent-upgrade-0.14.0/$STAMP"
    export SERVER_DATA_BACKUP_DIR="$BACKUP_DIR"
    install -d -m 0700 "$BACKUP_DIR"
    umask 077
    printf 'UTC=%s\nSTAMP=%s\nBACKUP_DIR=%s\n' \
      "$(date -u +%FT%TZ)" "$STAMP" "$BACKUP_DIR" \
      | tee "$BACKUP_DIR/window-start.txt"
    stat -c '%a %U:%G %n' "$BACKUP_DIR"
  fi
else
  echo 'STOP: operator 主機必須使用 bash 4+ 與 GNU coreutils stat／split／sha256sum' >&2
  false
fi

download_remote_file_in_parts() {
  local pod="$1" container="$2" remote_file="$3" local_file="$4"
  local remote_prefix="$5" expected_sha="$6" expected_bytes="$7"
  local part_dir="${local_file}.parts" manifest="${local_file}.parts.sha256"
  local candidate="${local_file}.candidate"
  local remote_part_prefix="/tmp/${remote_prefix}.part-"
  local split_rc part remote_sha_line remote_sha remote_sha_rc
  local local_part local_sha stream_rc attempt failures part_ok abort
  local candidate_sha candidate_bytes
  local -a parts PART_MANIFEST_PIPESTATUS

  [[ "$expected_sha" =~ ^[0-9a-f]{64}$ ]] || return 1
  [[ "$expected_bytes" =~ ^[0-9]+$ ]] || return 1
  rm -rf "$part_dir"
  rm -f "$local_file" "$candidate" "$manifest"
  install -d -m 0700 "$part_dir" || return 1
  kubectl --context woow-k3s -n omnigent exec "$pod" -c "$container" -- \
    sh -ceu '
      remote_file="$1"
      part_prefix="$2"
      rm -f "${part_prefix}"*
      split -b 32m -a 3 "$remote_file" "$part_prefix"
    ' sh "$remote_file" "$remote_part_prefix"
  split_rc="$?"
  mapfile -t parts < <(kubectl --context woow-k3s -n omnigent exec \
    "$pod" -c "$container" -- sh -c '
      part_prefix="$1"
      for f in "${part_prefix}"*; do
        [ -f "$f" ] || continue
        basename "$f"
      done
    ' sh "$remote_part_prefix" | tr -d '\r' | sort)
  [ "$split_rc" -eq 0 ] && [ "${#parts[@]}" -ge 1 ] || return 1

  : > "$manifest"
  abort=0
  for part in "${parts[@]}"; do
    remote_sha_line="$(kubectl --context woow-k3s -n omnigent exec \
      "$pod" -c "$container" -- sha256sum "/tmp/$part")"
    remote_sha_rc="$?"
    remote_sha="${remote_sha_line%% *}"
    if [ "$remote_sha_rc" -ne 0 ] \
      || [[ ! "$remote_sha" =~ ^[0-9a-f]{64}$ ]]; then
      abort=1
      break
    fi
    local_part="$part_dir/$part"
    failures=0
    part_ok=0
    for attempt in {1..3}; do
      rm -f "$local_part"
      printf 'download part=%s attempt=%s utc=%s\n' \
        "$part" "$attempt" "$(date -u +%FT%TZ)"
      kubectl --context woow-k3s -n omnigent exec "$pod" -c "$container" -- \
        sh -c 'cat "$1"; sleep 20' sh "/tmp/$part" > "$local_part"
      stream_rc="$?"
      local_sha="$(sha256sum "$local_part" | awk '{print $1}')"
      if [ "$stream_rc" -eq 0 ] && [ "$local_sha" = "$remote_sha" ]; then
        printf '%s  %s\n' "$local_sha" "$part" | tee -a "$manifest"
        PART_MANIFEST_PIPESTATUS=("${PIPESTATUS[@]}")
        if [ "${PART_MANIFEST_PIPESTATUS[*]}" = '0 0' ]; then
          part_ok=1
          break
        fi
      fi
      failures="$((failures + 1))"
      printf 'download failure: part=%s attempt=%s rc=%s remote_sha=%s local_sha=%s consecutive=%s\n' \
        "$part" "$attempt" "$stream_rc" "$remote_sha" "$local_sha" "$failures" >&2
      if [ "$failures" -ge 3 ]; then
        abort=1
        break
      fi
    done
    if [ "$part_ok" -ne 1 ]; then
      abort=1
      break
    fi
  done
  [ "$abort" -eq 0 ] || return 1

  cat "$part_dir"/* > "$candidate" || return 1
  candidate_sha="$(sha256sum "$candidate" | awk '{print $1}')" || return 1
  candidate_bytes="$(stat -c '%s' "$candidate")" || return 1
  [ "$candidate_sha" = "$expected_sha" ] \
    && [ "$candidate_bytes" = "$expected_bytes" ] || return 1
  mv -f "$candidate" "$local_file" || return 1
  chmod 0600 "$local_file" || return 1
  kubectl --context woow-k3s -n omnigent exec "$pod" -c "$container" -- \
    sh -ceu 'part_prefix="$1"; rm -f "${part_prefix}"*' \
    sh "$remote_part_prefix" || return 1
  rm -rf "$part_dir"
}

upload_local_file_in_parts() {
  local local_file="$1" pod="$2" container="$3" remote_candidate="$4"
  local remote_prefix="$5" expected_sha="$6" expected_bytes="$7"
  local part_dir="${local_file}.upload-parts"
  local remote_part_prefix="/tmp/${remote_prefix}.part-"
  local part_path part local_sha upload_output upload_rc remote_sha
  local attempt failures part_ok abort remote_count
  local remote_sha_line remote_bytes_line remote_sha_full remote_bytes_full
  local -a parts

  [[ "$expected_sha" =~ ^[0-9a-f]{64}$ ]] || return 1
  [[ "$expected_bytes" =~ ^[0-9]+$ ]] || return 1
  rm -rf "$part_dir"
  install -d -m 0700 "$part_dir" || return 1
  split -b 32m -a 3 "$local_file" "$part_dir/${remote_prefix}.part-" || return 1
  mapfile -t parts < <(find "$part_dir" -maxdepth 1 \
    -type f -name "${remote_prefix}.part-*" -print | sort)
  [ "${#parts[@]}" -ge 1 ] || return 1
  kubectl --context woow-k3s -n omnigent exec "$pod" -c "$container" -- \
    sh -ceu 'part_prefix="$1"; candidate="$2"; rm -f "${part_prefix}"* "$candidate"' \
    sh "$remote_part_prefix" "$remote_candidate" || return 1

  abort=0
  for part_path in "${parts[@]}"; do
    part="$(basename "$part_path")"
    local_sha="$(sha256sum "$part_path" | awk '{print $1}')" || return 1
    failures=0
    part_ok=0
    for attempt in {1..3}; do
      printf 'upload part=%s attempt=%s utc=%s\n' \
        "$part" "$attempt" "$(date -u +%FT%TZ)"
      upload_output="$(kubectl --context woow-k3s -n omnigent exec -i \
        "$pod" -c "$container" -- \
        sh -c 'cat > "/tmp/$1"; sha256sum "/tmp/$1"' sh "$part" \
        < "$part_path")"
      upload_rc="$?"
      remote_sha="${upload_output%% *}"
      if [ "$upload_rc" -eq 0 ] && [ "$remote_sha" = "$local_sha" ]; then
        printf 'upload part verified: part=%s attempt=%s local_sha=%s remote_sha=%s\n' \
          "$part" "$attempt" "$local_sha" "$remote_sha"
        part_ok=1
        break
      fi
      failures="$((failures + 1))"
      printf 'upload failure: part=%s attempt=%s rc=%s local_sha=%s remote_sha=%s consecutive=%s\n' \
        "$part" "$attempt" "$upload_rc" "$local_sha" "$remote_sha" "$failures" >&2
      if [ "$failures" -ge 3 ]; then
        abort=1
        break
      fi
    done
    if [ "$part_ok" -ne 1 ]; then
      abort=1
      break
    fi
  done
  [ "$abort" -eq 0 ] || return 1

  remote_count="$(kubectl --context woow-k3s -n omnigent exec \
    "$pod" -c "$container" -- sh -c '
      part_prefix="$1"
      count=0
      for f in "${part_prefix}"*; do
        [ -f "$f" ] || continue
        count=$((count + 1))
      done
      printf "%s\n" "$count"
    ' sh "$remote_part_prefix")" || return 1
  [ "$remote_count" -eq "${#parts[@]}" ] || return 1
  kubectl --context woow-k3s -n omnigent exec "$pod" -c "$container" -- \
    sh -ceu '
      part_prefix="$1"
      candidate="$2"
      cat "${part_prefix}"* > "$candidate"
    ' sh "$remote_part_prefix" "$remote_candidate" || return 1
  remote_sha_line="$(kubectl --context woow-k3s -n omnigent exec \
    "$pod" -c "$container" -- sha256sum "$remote_candidate")" || return 1
  remote_bytes_line="$(kubectl --context woow-k3s -n omnigent exec \
    "$pod" -c "$container" -- wc -c "$remote_candidate")" || return 1
  remote_sha_full="${remote_sha_line%% *}"
  remote_bytes_full="$(printf '%s\n' "$remote_bytes_line" | awk '{print $1}')"
  [ "$remote_sha_full" = "$expected_sha" ] \
    && [ "$remote_bytes_full" = "$expected_bytes" ] || return 1
  kubectl --context woow-k3s -n omnigent exec "$pod" -c "$container" -- \
    sh -ceu 'part_prefix="$1"; rm -f "${part_prefix}"*' \
    sh "$remote_part_prefix" || return 1
  rm -rf "$part_dir"
}
```

每個 fenced block 必須整塊執行，不得在行尾 `\` 的續行處切段。operator 若要新增或改寫 segment，必須先把完整 segment 貼到 pkg #3，取得裁決後才執行；不得只在本機 scratchpad 改命令。

### 步驟 3：確認無 running session，保存 host 快照

**執行者＝叢集運維｜證據＝貼 pkg #3**

以 admin token 對 `/v1/sessions` 唯讀確認沒有可見的 running session，並保存 `/v1/hosts` 的 `name`／`status` 快照。token 不得寫入 issue、shell history 或證據檔；證據只保留脫敏後欄位。

上游 v0.14.0 的 session list 回應是 `PaginatedList`（`omnigent/server/schemas.py:37-60`），資料在 `.data`，且 `has_more` 必須為 `false`；session status 也可能是 `waiting`（`schemas.py:2775`），因此它與 `running` 都會阻擋窗口。`kind=any` 才同時含 top-level 與 sub-agent session（`omnigent/server/routes/sessions/routes_core.py:1107-1122`）。hosts 回應則是 `{"hosts": [...]}`（`omnigent/server/routes/hosts.py:640`）。

```bash

  'https://omnigent.woowtech.io/v1/sessions?limit=1000&kind=any&visibility=all' \
  | jq '{blocking: [.data[] | select(.status == "running" or .status == "waiting") | {id,status}], has_more}' \
  | tee "$BACKUP_DIR/sessions.before.json"
SESSIONS_PIPESTATUS=("${PIPESTATUS[@]}")
printf 'sessions pipeline status=%s\n' "${SESSIONS_PIPESTATUS[*]}"
test "${SESSIONS_PIPESTATUS[*]}" = '0 0 0' || {
  echo 'STOP: sessions curl／jq／tee pipeline 失敗，停止並查明' >&2
  false
}

curl -fsS -H "Authorization: Bearer $OMNIGENT_ADMIN_TOKEN" \
  https://omnigent.woowtech.io/v1/hosts \
  | jq '[.hosts[] | {name,status}]' \
  | tee "$BACKUP_DIR/hosts.before.json"
HOSTS_PIPESTATUS=("${PIPESTATUS[@]}")
printf 'hosts pipeline status=%s\n' "${HOSTS_PIPESTATUS[*]}"
test "${HOSTS_PIPESTATUS[*]}" = '0 0 0' || {
  echo 'STOP: hosts curl／jq／tee pipeline 失敗，停止並查明' >&2
  false
}
```

`sessions.before.json` 的 `blocking`（`running` 或 `waiting`）必須為空、`has_more` 必須是 `false`，否則停止，不得 scale server。兩個 endpoint 都只列 token 持有者可見的資料；`/v1/hosts` 更明確只列 authenticated user 擁有的 host（`hosts.py:585`）。因此這不是「全站無 running session」的充分證明，全站安全仍依賴 T-1h 派工凍結與 host 擁有者盤點。

```bash
      printf 'DUMP_SHA_REMOTE=%s\nDUMP_BYTES_REMOTE=%s\n' \
        "$DUMP_SHA_REMOTE" "$DUMP_BYTES_REMOTE" \
        | tee "$BACKUP_DIR/pre-0140.remote.env"
    else
      echo 'STOP: 無法取得有效的 pod dump bytes／sha256；不得進步驟 9' >&2
      false
    fi
  else
    echo 'STOP: dump／目錄列舉／full-read 失敗；不得建立 evidence 或進步驟 9' >&2
    false
  fi
else
  false
fi
```

`pg_restore -l` 成功只證明目錄可讀；`pg_restore -f /dev/null` exit 0 才是整份 archive 已讀完。**進入步驟 9 前，必須把上方 pod 端 bytes、sha256 與 full-read PASS 原始 stdout 貼到 pkg #3。**步驟 8 已移到步驟 15 後以縮短 server=0 時間；因此 apply 時 dump 仍只在 postgres pod `/tmp`，尚沒有 off-cluster copy。這項取捨與 B1 的 pod-resident 路徑必須由 rollback 決策者知悉。

> **順序調整：**步驟 8 已移到步驟 15 驗收通過之後。步驟編號保留是為了和既有 WP-7 證據對照；進入步驟 9 前只需要完成步驟 7 的 pod 端 full-read、bytes／sha256 與 issue 證據。

### 步驟 9：建立兩顆手動 Longhorn snapshot

**執行者＝叢集運維｜證據＝貼 pkg #3**

server 必須仍為 0。WP-7 已實測以 Longhorn `Snapshot` CR 建立兩顆 snapshot；不用 UI，才能讓同一個強制 gate 與 mutation 位於同一個控制流。目標 PVC：

- `data-omnigent-postgres-0`
- `omnigent-server-data`

先取得實際 PV 名稱，再只在 gate 通過時 `create`（不是 `apply`）兩顆 CR：

```bash

  data-omnigent-postgres-0 -o jsonpath='{.spec.volumeName}')"
POSTGRES_PV_RC="$?"
SERVER_PV="$(kubectl --context woow-k3s -n omnigent get pvc \
  omnigent-server-data -o jsonpath='{.spec.volumeName}')"
SERVER_PV_RC="$?"

  && [ -n "$POSTGRES_PV" ] && [ -n "$SERVER_PV" ] \
  && require_server_zero; then
  SNAP_STAMP="$(printf '%s' "$STAMP" | tr 'A-Z' 'a-z')"
  POSTGRES_SNAP="pre-0140-${SNAP_STAMP}-pg"
  SERVER_SNAP="pre-0140-${SNAP_STAMP}-server"

apiVersion: longhorn.io/v1beta2
kind: Snapshot
metadata:
  name: ${POSTGRES_SNAP}
  namespace: longhorn-system
spec:
  volume: ${POSTGRES_PV}
  createSnapshot: true
---
apiVersion: longhorn.io/v1beta2
kind: Snapshot
metadata:
  name: ${SERVER_SNAP}
  namespace: longhorn-system
spec:
  volume: ${SERVER_PV}
  createSnapshot: true
YAML
  SNAP_CREATE_PIPESTATUS=("${PIPESTATUS[@]}")
  if [ "${SNAP_CREATE_PIPESTATUS[*]}" = '0 0' ]; then
    SNAPSHOTS_CREATED=1
    printf 'POSTGRES_PV=%s\nSERVER_PV=%s\nPOSTGRES_SNAP=%s\nSERVER_SNAP=%s\n' \
      "$POSTGRES_PV" "$SERVER_PV" "$POSTGRES_SNAP" "$SERVER_SNAP" \
      | tee "$BACKUP_DIR/longhorn-pvs.txt"
  else
    printf 'STOP: Snapshot CR create pipeline status=%s\n' \
      "${SNAP_CREATE_PIPESTATUS[*]}" >&2
    false
  fi
else
  echo 'STOP: PV 查詢或 server-zero gate 失敗；禁止建立 snapshot' >&2
  false
fi
```

這輪不設 backup target。server=0 且連線已排空，因此建立 snapshot 前不另跑 `CHECKPOINT`。建立後，兩顆 PV 都必須查到本窗口 snapshot 且 `readyToUse=true`：

```bash
SNAPSHOT_READY_DEADLINE="$(( $(date -u +%s) + 300 ))"
SNAPSHOTS_READY=0
if [ "$SNAPSHOTS_CREATED" -eq 1 ]; then
  while [ "$(date -u +%s)" -lt "$SNAPSHOT_READY_DEADLINE" ]; do
    POSTGRES_SNAP_READY="$(kubectl --context woow-k3s -n longhorn-system \
      get snapshots.longhorn.io "$POSTGRES_SNAP" \
      -o jsonpath='{.status.readyToUse}')"
    POSTGRES_SNAP_READY_RC="$?"
    SERVER_SNAP_READY="$(kubectl --context woow-k3s -n longhorn-system \
      get snapshots.longhorn.io "$SERVER_SNAP" \
      -o jsonpath='{.status.readyToUse}')"
    SERVER_SNAP_READY_RC="$?"
    printf 'snapshot ready: postgres=%s(rc=%s) server=%s(rc=%s) utc=%s\n' \
      "$POSTGRES_SNAP_READY" "$POSTGRES_SNAP_READY_RC" \
      "$SERVER_SNAP_READY" "$SERVER_SNAP_READY_RC" "$(date -u +%FT%TZ)"
    if [ "$POSTGRES_SNAP_READY_RC" -eq 0 ] \
      && [ "$SERVER_SNAP_READY_RC" -eq 0 ] \
      && [ "$POSTGRES_SNAP_READY" = true ] \
      && [ "$SERVER_SNAP_READY" = true ]; then
      SNAPSHOTS_READY=1
      break
    fi
    sleep 5
  done
fi
if [ "$SNAPSHOTS_READY" -eq 1 ]; then
  kubectl --context woow-k3s -n longhorn-system get snapshots.longhorn.io \
    "$POSTGRES_SNAP" "$SERVER_SNAP" \
    -o custom-columns='NAME:.metadata.name,VOLUME:.spec.volume,READY:.status.readyToUse,CREATED:.metadata.creationTimestamp'
else
  echo 'STOP: Longhorn snapshots 未在 300 秒內全部 readyToUse=true' >&2
  false
fi
```

若要從 Longhorn snapshot 回滾，volume 必須進 maintenance mode；因此除了 server 保持 0，**postgres 也必須先 scale 0**。未同時滿足不得操作 snapshot restore。

### 步驟 13：處理 `--wait` 逾時

**執行者＝叢集運維｜證據＝貼 pkg #3**

**`pending-upgrade` 唯一例外程序：**只有 release 已因非預期中斷卡死在 `pending-upgrade`、標準 R2 被 `another operation ... is in progress` 阻擋時，才可刪除該 pending revision 的 Helm release Secret。此例外**僅限 pending-upgrade 卡死、經步驟 0 指定的 rollback 決策者同意、操作前後完整貼 pkg #3**；不得用於一般 `failed`／`deployed` 狀態，也不得刪錯 revision。

```bash

export PENDING_REV='TBD：填入 status 顯示的 pending revision 整數'
if [[ "$PENDING_REV" =~ ^[0-9]+$ ]]; then
  printf '將刪除 pending release Secret revision=%s\n' "$PENDING_REV"
  kubectl --context woow-k3s -n omnigent delete secret \
    "sh.helm.release.v1.omnigent.v${PENDING_REV}"
  helm --kube-context woow-k3s status omnigent -n omnigent
else
  echo 'STOP: pending revision 不是整數，停止並查明' >&2
  false
fi
```

刪除後必須先完成 Rollback B 的 B2／B3，確認 DB 是 `ga1b2c3d4e5f`，才可執行 R2。

```bash
      if [ "$PG_RESTORE_RC" -eq 0 ]; then
        export ROLLBACK_RESTORE_READY=1
        echo 'destructive pg_restore exit=0; B3 readiness marker set'
      else
        echo 'STOP: destructive pg_restore 失敗；保留 dump，禁止 B3／退 image' >&2
        false
      fi
    else
      echo 'STOP: omnigent DB 仍有 client 或 client 清理失敗，禁止 restore' >&2
      false
    fi
  fi
else
  echo 'STOP: B1 dump 未 ready 或 server-zero gate 失敗，禁止 destructive restore' >&2
  false
fi
```

這裡的 `--clean --create` 是 drop／recreate 備份中的 database；不得只把 `--clean` 對已 migrate 的 `omnigent` DB 就地套用。
