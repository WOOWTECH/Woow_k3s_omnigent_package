# Omnigent v0.14.0 production 升級／rollback runbook

> 適用環境：`woow-k3s`／namespace `omnigent`／Helm release `omnigent`
>
> 升級路徑：v0.12.0（Alembic `ga1b2c3d4e5f`）→ v0.14.0（Alembic `gg1b2c3d4e5f`）
>
> 追蹤與證據：[pkg #3](https://github.com/WOOWTECH/Woow_k3s_omnigent_package/issues/3)

這是 production 維護窗口的逐行操作手冊。只有**叢集運維**能執行；其他人只可覆核文件與證據。所有命令都必須明帶 `--context woow-k3s`（Helm 用 `--kube-context woow-k3s`）且只作用於 namespace `omnigent`。

## 絕對禁止

- ⛔ 不得執行 `helm rollback`：migration 後把 image 退回 v0.12.0、但 DB 仍停在 `gg…`，server 會 crash-loop。
- ⛔ 不得使用 `--atomic`：逾時時自動回退 image，具有相同風險。
- ⛔ 不得執行 `kubectl set image`：會繞過 repo values 與 `scripts/apply.sh` 的 retain preflight。
- ⛔ 不得執行 `helm get values omnigent`：既有 revision 的 values 含明文帳密。
- ⛔ rollback 前 `OMNIGENT_FEATURES` 不可含 `canvas`；v0.12.0 不認得此 key。

每一步的完整 stdout／stderr、UTC 時間、執行指令與 exit code 都貼到 pkg #3；不得只貼摘要。

### 步驟 0：確認 go/no-go 前置

**執行者＝叢集運維｜證據＝貼 pkg #3**

全部成立才開窗：

- WP-0b＝pkg PR #4（`chore/pin-0.12.0-harden`）已 merge，且 production revision 11 deployed。步驟 11 依賴該 PR 加入的 `server.replicas` values 與 startupProbe。
- WP-1 已 merge，`main` 是已覆核的 v0.14.0 chart。
- WP-6 A–C PASS，上節「WP-6 回填值」已全部改成實測數字，沒有任何 `TBD（WP-6 回填）`。
- T-24h 公告已發；T-1h 起 issue-leader／repo-leader／worker 派工已凍結。
- 對外維護窗口保留 90 分鐘：固定操作 20 分鐘＋dump 實測＋migration 實測 ×2＋`max(Rollback A, Rollback B)`。
- 已指定 rollback 決策者，且 elmo 主機備份目錄有足夠空間。

本 runbook 文件 PR 可在 PR #4 仍 open 時獨立 merge；這不會豁免 production 窗口對「PR #4 已 merge 且 revision 11 deployed」的前置條件。

PR #4 的 startupProbe 必須存在，且 `failureThreshold × periodSeconds` 必須涵蓋 WP-6 表中的 go/no-go 絕對門檻。原因是 upstream `deploy/docker/entrypoint.py:536` 先執行 `run_migrations()`，`:545` 才啟動 uvicorn；migration 期間 `/health` 不回應。沒有 startupProbe 時，liveness 約四分鐘就會 SIGKILL 正在執行 `DROP INDEX CONCURRENTLY` 的 server pod。PR #4 硬編 `periodSeconds: 10` × `failureThreshold: 90`＝900 秒＝15 分鐘；若 WP-6 量到 migration ×3 超過 15 分鐘，須先另開 chart PR 改大 `failureThreshold` 並 merge，才可開 production 窗口。

```bash
STARTUP_FAILURE_THRESHOLD="$(kubectl --context woow-k3s -n omnigent get deployment \
  omnigent-server \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="server")].startupProbe.failureThreshold}')"
STARTUP_PERIOD_SECONDS="$(kubectl --context woow-k3s -n omnigent get deployment \
  omnigent-server \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="server")].startupProbe.periodSeconds}')"
printf 'startupProbe.failureThreshold=%s\nstartupProbe.periodSeconds=%s\n' \
  "$STARTUP_FAILURE_THRESHOLD" "$STARTUP_PERIOD_SECONDS"
test -n "$STARTUP_FAILURE_THRESHOLD" && test -n "$STARTUP_PERIOD_SECONDS" || {
  echo 'STOP: startupProbe failureThreshold／periodSeconds 不存在；PR #4 尚未落地，停止並查明' >&2
  false
}
```

### 步驟 3：確認無 running session，保存 host 快照

**執行者＝叢集運維｜證據＝貼 pkg #3**

以 admin token 對 `/v1/sessions` 唯讀確認沒有可見的 running session，並保存 `/v1/hosts` 的 `name`／`status` 快照。token 不得寫入 issue、shell history 或證據檔；證據只保留脫敏後欄位。

上游 v0.14.0 的 session list 回應是 `PaginatedList`（`omnigent/server/schemas.py:37-60`），資料在 `.data`，且 `has_more` 必須為 `false`；session status 也可能是 `waiting`（`schemas.py:2775`），因此它與 `running` 都會阻擋窗口。`kind=any` 才同時含 top-level 與 sub-agent session（`omnigent/server/routes/sessions/routes_core.py:1107-1122`）。hosts 回應則是 `{"hosts": [...]}`（`omnigent/server/routes/hosts.py:640`）。

```bash
# 在終端 1 的受控 shell 讀取並 export；read -s 避免 token 寫進 history／畫面。
read -rsp 'OMNIGENT_ADMIN_TOKEN: ' OMNIGENT_ADMIN_TOKEN
printf '\n'
export OMNIGENT_ADMIN_TOKEN

curl -fsS -H "Authorization: Bearer $OMNIGENT_ADMIN_TOKEN" \
  'https://omnigent.woowtech.io/v1/sessions?limit=1000&kind=any&visibility=all' \
  | jq '{blocking: [.data[] | select(.status == "running" or .status == "waiting") | {id,status}], has_more}' \
  | tee "$BACKUP_DIR/sessions.before.json"
SESSIONS_PIPESTATUS=("${PIPESTATUS[@]}")
printf 'sessions pipeline status=%s\n' "${SESSIONS_PIPESTATUS[*]}"
test "${SESSIONS_PIPESTATUS[*]}" = '0 0 0' || {
  echo 'STOP: sessions curl／jq／tee pipeline 失敗，停止並查明' >&2
  false
}

curl -fsS -H "Authorization: Bearer $OMNIGENT_ADMIN_TOKEN" \
  https://omnigent.woowtech.io/v1/hosts \
  | jq '[.hosts[] | {name,status}]' \
  | tee "$BACKUP_DIR/hosts.before.json"
HOSTS_PIPESTATUS=("${PIPESTATUS[@]}")
printf 'hosts pipeline status=%s\n' "${HOSTS_PIPESTATUS[*]}"
test "${HOSTS_PIPESTATUS[*]}" = '0 0 0' || {
  echo 'STOP: hosts curl／jq／tee pipeline 失敗，停止並查明' >&2
  false
}
```

`sessions.before.json` 的 `blocking`（`running` 或 `waiting`）必須為空、`has_more` 必須是 `false`，否則停止，不得 scale server。兩個 endpoint 都只列 token 持有者可見的資料；`/v1/hosts` 更明確只列 authenticated user 擁有的 host（`hosts.py:585`）。因此這不是「全站無 running session」的充分證明，全站安全仍依賴 T-1h 派工凍結與 host 擁有者盤點。

## 備份：兩段檔案備份＋Longhorn snapshot

### 步驟 5：server 還活著時備份 `/data`

**執行者＝叢集運維｜證據＝貼 pkg #3**

```bash
SERVER_POD="$(kubectl --context woow-k3s -n omnigent get pod \
  -l app.kubernetes.io/component=server \
  -o jsonpath='{.items[0].metadata.name}')"
test -n "$SERVER_POD" || {
  echo 'STOP: 找不到 server pod，停止並查明' >&2
  false
}

kubectl --context woow-k3s -n omnigent exec "$SERVER_POD" -c server -- \
  sh -ceu '
    rm -f /tmp/server-data.tgz
    rc=0
    tar --warning=no-file-changed -czf /tmp/server-data.tgz -C / data || rc=$?
    [ "$rc" -le 1 ] || exit "$rc"
    tar tzf /tmp/server-data.tgz >/dev/null
    sha256sum /tmp/server-data.tgz
  '

SERVER_DATA_SHA_REMOTE="$(kubectl --context woow-k3s -n omnigent exec \
  "$SERVER_POD" -c server -- sha256sum /tmp/server-data.tgz | awk '{print $1}')"
kubectl --context woow-k3s -n omnigent cp -c server \
  "$SERVER_POD:/tmp/server-data.tgz" "$BACKUP_DIR/server-data.tgz"
chmod 0600 "$BACKUP_DIR/server-data.tgz"
SERVER_DATA_SHA_LOCAL="$(sha256sum "$BACKUP_DIR/server-data.tgz" | awk '{print $1}')"
test "$SERVER_DATA_SHA_LOCAL" = "$SERVER_DATA_SHA_REMOTE" || {
  echo 'STOP: server-data tar 雙端 sha256 不同，停止並查明' >&2
  false
}
tar tzf "$BACKUP_DIR/server-data.tgz" >/dev/null
echo 'local tar full-read: PASS'
printf '%s  server-data.tgz\n' "$SERVER_DATA_SHA_LOCAL" \
  | tee "$BACKUP_DIR/server-data.tgz.sha256"

kubectl --context woow-k3s -n omnigent exec "$SERVER_POD" -c server -- \
  rm -f /tmp/server-data.tgz
```

server 還活著時檔案可能在 tar 讀取期間變動；GNU tar 此時可回 exit 1。上面只容許 exit 0／1，並在 pod 與本機各做一次 `tar tzf` full-read；exit >1、archive 無法完整讀取或 sha256 不同一律停止。

### 步驟 9：建立兩顆手動 Longhorn snapshot

**執行者＝叢集運維｜證據＝貼 pkg #3**

server 必須仍為 0。由 Longhorn UI 對下列兩個 PVC 對應的 PV 各建立一顆 snapshot，名稱建議 `pre-0140-$STAMP`：

- `data-omnigent-postgres-0`
- `omnigent-server-data`

先取得實際 PV 名稱：

```bash
POSTGRES_PV="$(kubectl --context woow-k3s -n omnigent get pvc \
  data-omnigent-postgres-0 -o jsonpath='{.spec.volumeName}')"
SERVER_PV="$(kubectl --context woow-k3s -n omnigent get pvc \
  omnigent-server-data -o jsonpath='{.spec.volumeName}')"
printf 'POSTGRES_PV=%s\nSERVER_PV=%s\n' "$POSTGRES_PV" "$SERVER_PV" \
  | tee "$BACKUP_DIR/longhorn-pvs.txt"
```

這輪不設 backup target。server=0 且連線已排空，因此建立 snapshot 前不另跑 `CHECKPOINT`。建立後，兩顆 PV 都必須查到本窗口 snapshot 且 `readyToUse=true`：

```bash
kubectl --context woow-k3s -n longhorn-system get snapshots.longhorn.io \
  -l "longhornvolume=$POSTGRES_PV" \
  -o custom-columns='NAME:.metadata.name,VOLUME:.spec.volume,READY:.status.readyToUse,CREATED:.metadata.creationTimestamp'

kubectl --context woow-k3s -n longhorn-system get snapshots.longhorn.io \
  -l "longhornvolume=$SERVER_PV" \
  -o custom-columns='NAME:.metadata.name,VOLUME:.spec.volume,READY:.status.readyToUse,CREATED:.metadata.creationTimestamp'
```

若要從 Longhorn snapshot 回滾，volume 必須進 maintenance mode；因此除了 server 保持 0，**postgres 也必須先 scale 0**。未同時滿足不得操作 snapshot restore。

### 步驟 11：執行唯一一次正常 upgrade

**執行者＝叢集運維｜證據＝貼 pkg #3**

在 repo `main` 執行，命令不得增減參數：

```bash
set +e

  scripts/apply.sh upgrade \
  2>&1 | tee "$BACKUP_DIR/apply-upgrade.log"
```

### 步驟 12：同步監看 migration 與 Ready

**執行者＝叢集運維｜證據＝貼 pkg #3**

Rollback A 不是卡住 migration 的預設處置；此情境固定用已驗證的 pre-upgrade dump 做 Rollback B。若 go/no-go 在終端 1 的 `apply.sh upgrade` 尚未返回時觸發：

1. ⛔ 不得 Ctrl-C 或 kill `apply.sh`；這會讓 Helm release 卡在 `pending-upgrade`，後續 R2 會被 `another operation (install/upgrade/rollback) is in progress` 擋住，而一般解法 `helm rollback` 又在本輪禁用。
2. 直接在終端 2 開始 B1，把 server scale 回 0。終端 1 的 `helm upgrade --wait` 應把 replicas=0 視為 Ready、將 revision 12 標為 `deployed`，或到 30 分鐘標為 `failed`；兩者都能在 B2／B3 後進 R2。此行為必須先由 WP-6 沙盒演練確認並回填 pkg #3。
3. 等終端 1 自行返回，再記錄 `APPLY_RC` 與 `helm status`；不可跳過 release 狀態證據。

### 步驟 13：處理 `--wait` 逾時

**執行者＝叢集運維｜證據＝貼 pkg #3**

`--wait` 逾時不等於 migration 失敗，也不得因此 `helm rollback`。先唯讀盤點：

```bash

kubectl --context woow-k3s -n omnigent describe deployment omnigent-server
kubectl --context woow-k3s -n omnigent logs deployment/omnigent-server -c server --tail=-1
```

- 若超過「WP-6 回填值」表的 go/no-go 絕對門檻：依步驟 12 的 in-flight 程序走 Rollback B。
- 若 pod 後來 Ready、migration 與驗證皆成功，但 Helm release 因逾時仍標 `failed`：先跑 `check-drift.sh` 並確認 **check 2 全 MATCH**，再跑一次相同的 `CF_CREDS_JSON=/nonexistent TIMEOUT=30m KUBECONTEXT=woow-k3s scripts/apply.sh upgrade` 修正 release 狀態，並記錄 revision 增加。這是逾時後的狀態修正，不得加 `--atomic`。

**`pending-upgrade` 唯一例外程序：**只有 release 已因非預期中斷卡死在 `pending-upgrade`、標準 R2 被 `another operation ... is in progress` 阻擋時，才可刪除該 pending revision 的 Helm release Secret。此例外**僅限 pending-upgrade 卡死、經步驟 0 指定的 rollback 決策者同意、操作前後完整貼 pkg #3**；不得用於一般 `failed`／`deployed` 狀態，也不得刪錯 revision。

```bash
helm --kube-context woow-k3s status omnigent -n omnigent
export PENDING_REV='TBD：填入 status 顯示的 pending revision 整數'
if [[ "$PENDING_REV" =~ ^[0-9]+$ ]]; then
  printf '將刪除 pending release Secret revision=%s\n' "$PENDING_REV"
  kubectl --context woow-k3s -n omnigent delete secret \
    "sh.helm.release.v1.omnigent.v${PENDING_REV}"
  helm --kube-context woow-k3s status omnigent -n omnigent
else
  echo 'STOP: pending revision 不是整數，停止並查明' >&2
  false
fi
```

刪除後必須先完成 Rollback B 的 B2／B3，確認 DB 是 `ga1b2c3d4e5f`，才可執行 R2。

### 步驟 A2：用 v0.14.0 digest 建立一次性 downgrade Pod

**執行者＝叢集運維｜證據＝貼 pkg #3**

```bash

  --ignore-not-found
cat <<'YAML' | kubectl --context woow-k3s -n omnigent apply -f -

kind: Pod

  name: omnigent-db-downgrade-0140
  labels:
    app.kubernetes.io/name: omnigent
    app.kubernetes.io/component: db-downgrade
spec:
  restartPolicy: Never
  automountServiceAccountToken: false
  containers:
    - name: downgrade
      image: ghcr.io/omnigent-ai/omnigent-server:v0.14.0@sha256:9a964b9eb9c60122faf4f1fbbcd8e4284029978467dd3056871828c5df5e042f
      imagePullPolicy: IfNotPresent
      env:
        - name: POSTGRES_PASSWORD
          valueFrom:
            secretKeyRef:
              name: omnigent-postgres
              key: POSTGRES_PASSWORD
        - name: DATABASE_URL
          value: postgresql+psycopg://omnigent:$(POSTGRES_PASSWORD)@omnigent-postgres:5432/omnigent
      command: [/bin/sh, -ceu]
      args:
        - |
          python - <<'EOF'
          import os
          from alembic import command
          from omnigent.db.utils import _build_alembic_config, normalize_database_url

          command.downgrade(
              _build_alembic_config(
                  normalize_database_url(os.environ["DATABASE_URL"])
              ),
              "ga1b2c3d4e5f",
          )
          EOF
YAML

ROLLBACK_A_WAIT_LIMIT_MINUTES='TBD（從 WP-6 回填值表抄入整數分鐘）'
if [[ ! "$ROLLBACK_A_WAIT_LIMIT_MINUTES" =~ ^[0-9]+$ ]]; then
  echo 'STOP: A2 等待上限尚未由 WP-6 回填，停止並查明' >&2
  false
else
  A2_DEADLINE_EPOCH="$(( $(date -u +%s) + ROLLBACK_A_WAIT_LIMIT_MINUTES * 60 ))"
  PHASE=Pending
  while :; do
    PHASE="$(kubectl --context woow-k3s -n omnigent get pod \
      omnigent-db-downgrade-0140 -o jsonpath='{.status.phase}')"
    [ "$PHASE" = Succeeded ] && break
    [ "$PHASE" = Failed ] && break
    if [ "$(date -u +%s)" -ge "$A2_DEADLINE_EPOCH" ]; then
      PHASE=TimedOut
      break
    fi
    sleep 15
  done
  printf 'downgrade pod phase=%s\n' "$PHASE"
  kubectl --context woow-k3s -n omnigent logs omnigent-db-downgrade-0140 \
    | tee "$BACKUP_DIR/rollback-a-downgrade.log"
  case "$PHASE" in
    Succeeded) ;;
    *)
      echo 'STOP: Rollback A 未成功；不得重跑 A，直接走 Rollback B' >&2
      false
      ;;
  esac
fi
```
