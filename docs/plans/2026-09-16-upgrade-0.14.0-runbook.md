# Omnigent v0.14.0 production 升級／rollback runbook

> 適用環境：`woow-k3s`／namespace `omnigent`／Helm release `omnigent`
>
> 升級路徑：v0.12.0（Alembic `ga1b2c3d4e5f`）→ v0.14.0（Alembic `gg1b2c3d4e5f`）
>
> 追蹤與證據：[pkg #3](https://github.com/WOOWTECH/Woow_k3s_omnigent_package/issues/3)

這是 production 維護窗口的逐行操作手冊。只有**叢集運維**能執行；其他人只可覆核文件與證據。所有命令都必須明帶 `--context woow-k3s`（Helm 用 `--kube-context woow-k3s`）且只作用於 namespace `omnigent`。

## 絕對禁止

- ⛔ 不得執行 `helm rollback`：migration 後把 image 退回 v0.12.0、但 DB 仍停在 `gg…`，server 會 crash-loop。
- ⛔ 不得使用 `--atomic`：逾時時自動回退 image，具有相同風險。
- ⛔ 不得執行 `kubectl set image`：會繞過 repo values 與 `scripts/apply.sh` 的 retain preflight。
- ⛔ 不得執行 `helm get values omnigent`：既有 revision 的 values 含明文帳密。
- ⛔ rollback 前 `OMNIGENT_FEATURES` 不可含 `canvas`；v0.12.0 不認得此 key。

每一步的完整 stdout／stderr、UTC 時間、執行指令與 exit code 都貼到 pkg #3；不得只貼摘要。

| 項目 | 基線 |
| --- | --- |
| Alembic | `ga1b2c3d4e5f`（v0.12.0 head） |
| DB | 2339 MB |
| `conversation_items` | 2328 MB |
| `hosts` | 8 列／104 kB |
| GIN trigram index | `ix_conversation_items_search_text_trgm` 存在 |
| idle in transaction | 0 |
| postgres pod `/tmp` | overlay 可用 21.4 GB |
| cloudflared Secret | `omnigent-cloudflared-creds` resourceVersion `129097880` |
| Longhorn | `snapshots.longhorn.io` 等 CRD 存在；無 backup target、無既有 snapshot、無 VolumeSnapshot CRD |

v0.14.0 的 `gf1b2c3d4e5f` upgrade 會以 `DROP INDEX CONCURRENTLY` 移除上述 GIN index。Rollback A 的 downgrade 會在 transaction 內以非 CONCURRENTLY 的 `CREATE INDEX` 重建它；資料表約 2.3 GB，因此耗時必須先由 WP-6 量測。

## 備份：兩段檔案備份＋Longhorn snapshot

### 步驟 5：server 還活著時備份 `/data`

**執行者＝叢集運維｜證據＝貼 pkg #3**

```bash
SERVER_POD="$(kubectl --context woow-k3s -n omnigent get pod \
  -l app.kubernetes.io/component=server \
  -o jsonpath='{.items[0].metadata.name}')"
test -n "$SERVER_POD"

kubectl --context woow-k3s -n omnigent exec "$SERVER_POD" -c server -- \
  sh -ceu 'rm -f /tmp/server-data.tgz; tar czf /tmp/server-data.tgz -C / data; sha256sum /tmp/server-data.tgz'

SERVER_DATA_SHA_REMOTE="$(kubectl --context woow-k3s -n omnigent exec \
  "$SERVER_POD" -c server -- sha256sum /tmp/server-data.tgz | awk '{print $1}')"
kubectl --context woow-k3s -n omnigent cp -c server \
  "$SERVER_POD:/tmp/server-data.tgz" "$BACKUP_DIR/server-data.tgz"
chmod 0600 "$BACKUP_DIR/server-data.tgz"
SERVER_DATA_SHA_LOCAL="$(sha256sum "$BACKUP_DIR/server-data.tgz" | awk '{print $1}')"
test "$SERVER_DATA_SHA_LOCAL" = "$SERVER_DATA_SHA_REMOTE"
tar tzf "$BACKUP_DIR/server-data.tgz" >/dev/null
echo 'local tar full-read: PASS'
printf '%s  server-data.tgz\n' "$SERVER_DATA_SHA_LOCAL" \
  | tee "$BACKUP_DIR/server-data.tgz.sha256"

kubectl --context woow-k3s -n omnigent exec "$SERVER_POD" -c server -- \
  rm -f /tmp/server-data.tgz
```

```bash
kubectl --context woow-k3s -n omnigent exec omnigent-postgres-0 -c postgres -- \
  sh -ceu '
    rm -f /tmp/pre-0140.dump /tmp/pre-0140.list
    pg_dump -Fc -U omnigent -f /tmp/pre-0140.dump omnigent
    pg_restore -l /tmp/pre-0140.dump | tee /tmp/pre-0140.list
    pg_restore -f /dev/null /tmp/pre-0140.dump

```

### 步驟 9：建立兩顆手動 Longhorn snapshot

**執行者＝叢集運維｜證據＝貼 pkg #3**

server 必須仍為 0。由 Longhorn UI 對下列兩個 PVC 對應的 PV 各建立一顆 snapshot，名稱建議 `pre-0140-$STAMP`：

- `data-omnigent-postgres-0`
- `omnigent-server-data`

先取得實際 PV 名稱：

```bash
POSTGRES_PV="$(kubectl --context woow-k3s -n omnigent get pvc \
  data-omnigent-postgres-0 -o jsonpath='{.spec.volumeName}')"
SERVER_PV="$(kubectl --context woow-k3s -n omnigent get pvc \
  omnigent-server-data -o jsonpath='{.spec.volumeName}')"
printf 'POSTGRES_PV=%s\nSERVER_PV=%s\n' "$POSTGRES_PV" "$SERVER_PV" \
  | tee "$BACKUP_DIR/longhorn-pvs.txt"
```

這輪不設 backup target。server=0 且連線已排空，因此建立 snapshot 前不另跑 `CHECKPOINT`。建立後，兩顆 PV 都必須查到本窗口 snapshot 且 `readyToUse=true`：

```bash
kubectl --context woow-k3s -n longhorn-system get snapshots.longhorn.io \
  -l "longhornvolume=$POSTGRES_PV" \
  -o custom-columns='NAME:.metadata.name,VOLUME:.spec.volume,READY:.status.readyToUse,CREATED:.metadata.creationTimestamp'

kubectl --context woow-k3s -n longhorn-system get snapshots.longhorn.io \
  -l "longhornvolume=$SERVER_PV" \
  -o custom-columns='NAME:.metadata.name,VOLUME:.spec.volume,READY:.status.readyToUse,CREATED:.metadata.creationTimestamp'
```

若要從 Longhorn snapshot 回滾，volume 必須進 maintenance mode；因此除了 server 保持 0，**postgres 也必須先 scale 0**。未同時滿足不得操作 snapshot restore。

**執行者＝叢集運維｜證據＝貼 pkg #3**


**執行者＝叢集運維｜證據＝貼 pkg #3**

**Go/no-go：任一條成立，停止等待並直接走 Rollback B：**

1. migration 耗時超過 WP-6 實測值 ×3；或
2. 自 `UPGRADE_T0` 起 T+45 分 server 仍未 Ready。

Rollback A 不是卡住 migration 的預設處置；此情境固定用已驗證的 pre-upgrade dump 做 Rollback B。

### 步驟 13：處理 `--wait` 逾時

**執行者＝叢集運維｜證據＝貼 pkg #3**

`--wait` 逾時不等於 migration 失敗，也不得因此 `helm rollback`。先唯讀盤點：

```bash

kubectl --context woow-k3s -n omnigent get pods -o wide
kubectl --context woow-k3s -n omnigent describe deployment omnigent-server
kubectl --context woow-k3s -n omnigent logs deployment/omnigent-server -c server --tail=-1
```

- 若超過上述 ×3 或 T+45 門檻：Rollback B。
- 若 pod 後來 Ready、migration 與驗證皆成功，但 Helm release 因逾時仍標 `failed`：只在確認 render 無變更後，再跑一次相同的 `CF_CREDS_JSON=/nonexistent TIMEOUT=30m KUBECONTEXT=woow-k3s scripts/apply.sh upgrade` 修正 release 狀態，並記錄 revision 增加。這是逾時後的狀態修正，不得加 `--atomic`。

## Rollback A：Alembic downgrade

Rollback A 適用於 v0.14.0 migration 已完成、DB 可正常連線且 downgrade 演練耗時仍在窗口預算內。若 migration 卡住、archive／DB 狀態可疑、soft-deleted host 非 0，改走 Rollback B。

### 步驟 A1：scale server 0 並檢查 soft-deleted host

**執行者＝叢集運維｜證據＝貼 pkg #3**

```bash
kubectl --context woow-k3s -n omnigent scale deployment/omnigent-server --replicas=0
kubectl --context woow-k3s -n omnigent wait --for=delete pod \
  -l app.kubernetes.io/component=server --timeout=5m
kubectl --context woow-k3s -n omnigent exec omnigent-postgres-0 -c postgres -- \
  psql -U omnigent -d omnigent -Atc \
  "select count(*) from hosts where deleted_at is not null;"
```

結果必須是 `0`。`gc` downgrade 會 drop `deleted_at`；非 0 代表 soft-deleted host 會復活，此時停止 A 並改走 B。

### 步驟 A2：用 v0.14.0 digest 建立一次性 downgrade Pod

**執行者＝叢集運維｜證據＝貼 pkg #3**

```bash

  --ignore-not-found
```

## Rollback B：restore pre-upgrade dump

Rollback B 會把整顆 DB 回到備份時點；升級後新增資料會遺失。這是 migration 超過 go/no-go 門檻或 Rollback A 不安全／失敗時的預設方案。

### 步驟 B1：保持 server 0，把已校驗 dump copy 回 postgres pod

**執行者＝叢集運維｜證據＝貼 pkg #3**

```bash
kubectl --context woow-k3s -n omnigent scale deployment/omnigent-server --replicas=0
kubectl --context woow-k3s -n omnigent wait --for=delete pod \
  -l app.kubernetes.io/component=server --timeout=5m
(cd "$BACKUP_DIR" && sha256sum -c pre-0140.dump.sha256)

kubectl --context woow-k3s -n omnigent cp -c postgres \
  "$BACKUP_DIR/pre-0140.dump" omnigent-postgres-0:/tmp/pre-0140.dump
DUMP_SHA_REMOTE="$(kubectl --context woow-k3s -n omnigent exec \
  omnigent-postgres-0 -c postgres -- sha256sum /tmp/pre-0140.dump | awk '{print $1}')"
DUMP_SHA_LOCAL="$(sha256sum "$BACKUP_DIR/pre-0140.dump" | awk '{print $1}')"
test "$DUMP_SHA_REMOTE" = "$DUMP_SHA_LOCAL"
```

### 步驟 B2：drop／recreate 整顆 DB 並 restore

**執行者＝叢集運維｜證據＝貼 pkg #3**

先確認除目前檢查外沒有 client，再從 maintenance DB `postgres` 執行完整 restore：

```bash
kubectl --context woow-k3s -n omnigent exec omnigent-postgres-0 -c postgres -- \
  psql -U omnigent -d postgres -Atc \
  "select count(*) from pg_stat_activity where datname='omnigent';"

kubectl --context woow-k3s -n omnigent exec omnigent-postgres-0 -c postgres -- \
  pg_restore -U omnigent -d postgres --clean --create --if-exists \
  /tmp/pre-0140.dump
```

這裡的 `--clean --create` 是 drop／recreate 備份中的 database；不得只把 `--clean` 對已 migrate 的 `omnigent` DB 就地套用。

### 步驟 B3：驗證 restore head 並清掉 pod 內 dump

**執行者＝叢集運維｜證據＝貼 pkg #3**

```bash

```

Alembic 必須只有 `ga1b2c3d4e5f` 才可退 image。

### Longhorn snapshot 災難備援

**執行者＝叢集運維｜證據＝貼 pkg #3**

只有 dump restore 無法使用時才採 snapshot。先把兩個 workload 都停掉：

```bash
kubectl --context woow-k3s -n omnigent scale deployment/omnigent-server --replicas=0
kubectl --context woow-k3s -n omnigent scale statefulset/omnigent-postgres --replicas=0
kubectl --context woow-k3s -n omnigent wait --for=delete pod \
  -l app.kubernetes.io/component=server --timeout=5m
kubectl --context woow-k3s -n omnigent wait --for=delete pod \
  -l app.kubernetes.io/component=postgres --timeout=5m
```

確認 Pod 全消失後，才可在 Longhorn UI 將目標 volume 進 maintenance mode 並從本窗口 `readyToUse=true` 的 snapshot restore。完成、退出 maintenance mode、volume healthy 後先把 postgres scale 回 1，驗 `alembic_version=ga1b2c3d4e5f`，再走下一節的 v0.12.0 image 退回。每個 UI 動作與 snapshot 名稱都貼 pkg #3。

## A／B 共用：退回 v0.12.0 image

### 步驟 R1：確認 DB head 與 feature flags

**執行者＝叢集運維｜證據＝貼 pkg #3**

```bash
kubectl --context woow-k3s -n omnigent exec omnigent-postgres-0 -c postgres -- \

FEATURES="$(kubectl --context woow-k3s -n omnigent get deployment omnigent-server \

printf 'OMNIGENT_FEATURES=%s\n' "$FEATURES"

  *,canvas,*) echo 'BLOCK: v0.12.0 不支援 canvas' >&2; exit 1 ;;

```

DB 必須是 `ga1b2c3d4e5f`，features 不得含 `canvas`。

### 步驟 R2：用 apply.sh 退 image

**執行者＝叢集運維｜證據＝貼 pkg #3**

```bash
CF_CREDS_JSON=/nonexistent TIMEOUT=30m KUBECONTEXT=woow-k3s \
  scripts/apply.sh upgrade \
  --set server.image=ghcr.io/omnigent-ai/omnigent-server:v0.12.0@sha256:caa84ada76a34857e297f12d2a82b0cfb12ca03755df31c40d1d30bd37a3730e
```
