**首次 deploy 遇到的 bug（本 PR 已修）**：runner-loop 的 `sleep infinity on login failure`（upstream 設計）races post-install Job，first-boot 3 個 runner 全部 login fail → 手動 restart 才好。修法：在 runner Deployment 加 `initContainer wait-admin-claim`，poll `/v1/info` 直到 `needs_setup=false` 才啟 runner-loop。修完 `helm upgrade` 後 3 runners restart，30 秒內全部 online 註冊。

## 3. Cloudflared tunnel 建置流程（可 reproducible）

```bash
# 1. Create tunnel (CF API)
TUNNEL_ID=$(curl -sS -H "Authorization: Bearer $CF_TOKEN" -H 'Content-Type: application/json' \
  -X POST "https://api.cloudflare.com/client/v4/accounts/${ACCT}/cfd_tunnel" \
  --data '{"name":"omnigent-k3s","config_src":"cloudflare",
           "tunnel_secret":"'"$(openssl rand -base64 32)"'"}' \
  | jq -r .result.id)

# 2. Push ingress config (route omnigent.woowtech.io -> in-cluster svc)
curl -sS -H "Authorization: Bearer $CF_TOKEN" -H 'Content-Type: application/json' \
  -X PUT "https://api.cloudflare.com/client/v4/accounts/${ACCT}/cfd_tunnel/${TUNNEL_ID}/configurations" \
  --data '{"config":{"ingress":[
    {"hostname":"omnigent.woowtech.io",
     "service":"http://omnigent-server.omnigent.svc.cluster.local:8000"},
    {"service":"http_status:404"}]}}'

# 3. DNS CNAME
curl -sS -H "Authorization: Bearer $CF_TOKEN" -H 'Content-Type: application/json' \
  -X POST "https://api.cloudflare.com/client/v4/zones/${ZONE}/dns_records" \
  --data "{\"type\":\"CNAME\",\"name\":\"omnigent\",
           \"content\":\"${TUNNEL_ID}.cfargotunnel.com\",
           \"ttl\":1,\"proxied\":true}"
```

`scripts/apply.sh` 讀 `/tmp/omnigent-tunnel-creds.json`（`{AccountTag,TunnelID,TunnelSecret}` 三欄），自動建 k8s Secret 給 cloudflared sidecar 掛。

## 4. Sub-agent 平行測試結果

### 🅰️ API smoke（全端點掃）

跟 podman 姊妹幾乎 1:1 一樣。差異只在 `/v1/hosts` 現在有 6 個（3 online + 3 offline 舊 replica），CF edge header 有 `cf-ray`/`server: cloudflare`/`cf-cache-status`。

**同樣 HIGH 未修**：
- 🔴 **登入無 rate limit**：30 次錯密碼 401 全過，無 429 無 backoff。CF edge 也沒加 throttle。
- 🔴 **`/healthz` 被 SPA catch-all 吃**：回 HTML 200；我方 chart 已改成 probe `/health`
- ⚠️ **CF 沒 cap body size**：5MB POST 完整 parse 到 origin FastAPI 才 422（origin 依然無 size middleware，跟 podman 一樣）

**新觀察**：
- `curl -I /health` 回 404（HEAD verb 沒 wire），`curl GET /health` 才 200。可能 CF 或 FastAPI route 只註冊 GET。
- 3 個 stale offline host 沒 GC — pod 每次 rolling restart 都留一個舊 host_id 在 `/v1/hosts`。

### 🅱️ Resilience（`kubectl delete pod --force` 全套）

**5 個情境全 PASS**：

| # | 情境 | pod Ready | `/health` 200 | Restarts | Public 停 | 判定 |
|---|---|---|---|---|---|---|
| 1 | Kill `omnigent-server` | 14s | 14s | 0 | ~10s (t=1-13s 502) | ✅ PASS |
| 2 | Kill runner `pi1` | 20s | pi1 re-registered 23s | 0 | 0s（pi4/pi5 continuously online） | ✅ PASS |
| 3 | Kill `omnigent-postgres-0` (STS, Longhorn RWO re-attach) | pg Ready 41s，`/health` 200 133s | 1 (server pod restart via liveness) | **~125s** | ✅ PASS w/ caveat |
| 4 | 同時 kill 兩個 cloudflared | 2s（並發） | — | 0 | **1s** (t=1 single 502) | ✅ PASS |
| 5 | 同時 kill 全部 3 個 runner | all Ready 34s，all re-registered 39s | — | 0 | 0s (server 不受影響) | ✅ PASS |

**Test 5 特別重要**：驗證我方本 PR 新加的 `wait-admin-claim` initContainer 修復 — 沒有這個初始化步驟，restart 後的 runner-loop 會 race post-install Job 然後 `sleep infinity`。3 個並發重啟都 clean re-register，證明修復穩定。

**Test 3 caveat**：Postgres re-attach 41s 內完成，但 server pod 沒 app-level DB retry；靠 kubelet liveness probe restart server（RESTARTS 0→1），總 downtime ~125s。**建議 follow-up**：加 app-level Postgres reconnect loop，降到 <30s。

**Test 4 亮點**：Cloudflare edge tunnel keep-alive 讓兩個 cloudflared pod 同時死也只掉 1 秒（比預期的 15s 好很多）。

### 🆎 K3S-INFRA 觀察

- **Auto-recovery 全 Kubernetes-native**：5 種殺法零手動介入。生產 pod-level 失效可用。
- **Stale offline host 累積**：測試跑完 `/v1/hosts` 有 3 online + **7 offline**（每次 pod restart 累一個）。同 podman 姊妹的 W2-HIGH-3。
- **Runner blast radius bounded**：killing pi1 從未影響 pi4/pi5。UI 端 Host picker 反應即時。

### 🅲️ Automation E2E — sub-agent 完整 run

**FAIL as expected**（K3S-HIGH-4 root cause 已鎖定）：
- 建 task `54e2db6c32904ced8f53d4cb44b1e505` (hourly rrule to pi1 host)
- Scheduler 到 `next_run_at` **靜默 swallow**（沒 create run row），只 advance `next_run_at` — 這是**新 bug**（見下 K3S-MED-4）
- 手動 `POST /v1/scheduled-tasks/{id}/run` fire → `error_code=host_offline`，session_id null，assistant reply 從未產生
- Root cause 在 `/v1/hosts` 就見：所有 pi runner 的 `configured_harnesses.pi-native.status = "needs-auth"`
- 邏輯：scheduler 判 host 不可用 → `host_offline` — 儘管 `/v1/hosts` 頂層 `.status = "online"`

Schema 跟 podman 姊妹 **1:1**（`CreateScheduledTaskRequest` 欄位無變）。

Task 未刪（依 Q9 保留）：22:45:53 UTC 會再 fire 一次；若 seed 完成後 `pi-native` 從 `needs-auth` 變 `ready`，那次 fire 應該 PASS — 可當 regression gate。

### 🅳️ Chat e2e（main thread chrome-devtools MCP）

**同 automation E2E 原因**：session `Starting session` busy 卡住，pi 沒 provider 無法 respond。

**Workaround 已 shipped**：`scripts/seed-pi-from.sh <src-ns> <src-pod> <runner-host>`：
- 從 pi-agent-N pod（container `pi-web`）tar `/data/pi-agent/*`
- Stream 到 omnigent-runner-<host> pod（container `runner`）同 mount 路徑
- 排除 `lost+found`/`logs`/`missions/log`
- 若本機有 `pv` 帶進度條；否則 silent transfer
- 完成後 rollout restart runner 讓 runner-loop 重讀 providers

**跑法**：
```bash
KUBECONTEXT=woow-k3s NAMESPACE=omnigent \
  scripts/seed-pi-from.sh pi-agent-woow pi-agent-65669d447f-xmwbs pi1
```

**實測 timing**（本次跑）：pi-agent-1 source `/data/pi-agent` = 5.9 GB，透過 kubectl exec tar-pipe 走 WAN 傳輸 → 預估 40–60 分鐘 first seed，之後 runner 就自帶 provider。是 **one-time deployment cost**；重跑 chart 只要不刪 PVC 就不用再 seed。

**注意**：這只是 point-in-time snapshot，不是 live share（Longhorn RWO 限制 — Q5 選 (B) 的直接後果）。想要 live share 見 [`docs/plans/2026-08-31-initial-package.md`](../plans/2026-08-31-initial-package.md) 記錄的 (A)（sidecar）與 (C)（Longhorn VolumeSnapshot）方案。快速 alternative — 加 Longhorn `VolumeSnapshot` API 直接快照 pi-agent-N-data → 恢復成 omnigent-runner-piN-data PVC，數秒內完成。

## 6. 缺陷清單（新 / 沿用 podman）

### 🔴 HIGH — 4 項（3 沿用 + 1 新）

- **W2-HIGH-1 沿用**：登入無 rate limit（同 podman auth curl finding）
- **W2-HIGH-2 沿用**：`POST /v1/sessions` 無 body size cap；k3s + CF edge 也沒 cap
- **W2-HIGH-3 沿用**：runner pod 重啟 → 舊 host_id 留孤兒（UI Switch-Host modal 補上）
- **K3S-HIGH-4 新**：fresh runner PVC → pi 無 provider → chat / automation 都失效。**已 ship** `scripts/seed-pi-from.sh` 解 first-boot；長期解法要 upstream RWX Longhorn 或 chart 加 initContainer 做 `kubectl cp` 自動化

### ⚠️ MED — 4 項

- **K3S-MED-1**：3 個 stale offline host 沒 GC，每次 pod restart 累積一個（Test 5 kill 3 runner 後累到 3 online + 7 offline）
- **K3S-MED-2**：`curl -I /health` 回 404（HEAD verb 沒 wire）— cosmetic
- **K3S-MED-3**：runner-loop 若跑在 post-install Job 之前會 `sleep infinity` 卡死。**已修**（initContainer wait-admin-claim in runner-deployments.yaml）
- **K3S-MED-4 新**：scheduled-task auto-fire 遇到 `needs-auth` harness **靜默 swallow** — 只 advance `next_run_at`，不 create run row。手動 `POST /run` 才會產生 `error_code=host_offline` run。UX 上：user 建了 task，看 runs list 一直空，以為 scheduler 沒跑 — 其實是跑了但沒記
- **K3S-MED-5**：Postgres pod restart 後 server 沒 app-level DB reconnect loop → 靠 kubelet liveness restart server，總 downtime ~125s。建議 patch upstream 或 sidecar retry proxy

### ⚠️ LOW — 2 項

- **K3S-LOW-1**：cloudflared credentials Secret 是 apply.sh 手工 kubectl create（不是 Helm 管的） — 未來可加 sub-chart
- **K3S-LOW-2**：chart CI `chart.yml` 只 lint + kubeconform，未 publish 到 GHCR OCI helm chart registry
